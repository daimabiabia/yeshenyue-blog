# 时序数据库与数据上云速查

## 1. 为什么不用 MySQL 存传感器数据

| 维度 | MySQL | 时序库 TSDB |
|---|---|---|
| 写入 | 行存储，索引贵 | 追加写，百万点/秒 |
| 按时间聚合 | 慢 | 原生连续查询 |
| 降采样/保留策略 | 手写任务 | 内置（TTL 自动删旧数据） |
| 压缩 | 一般 | 列存+专用编码，10 倍压缩 |

## 2. 主流选手速览

| 库 | 特点 | 适合 |
|---|---|---|
| InfluxDB | 星标王，InfluxQL/Flux，v3 转向 Parquet | 通用首选 |
| TimescaleDB | PostgreSQL 扩展，SQL 全兼容 | 已有 PG 技术栈 |
| TDengine | 国产，超级表+标签概念，极致压缩 | 国产化/高吞吐 |
| Prometheus | 拉模式+PromQL，监控之王 | 运维监控 |
| AWS Timestream | 云托管无运维 | AWS 全家桶 |
| MQTT+EMQX 内置 | 轻量够用 | 小项目起步 |

## 3. 数据建模（以 InfluxDB 为例）

```text
measurement: device_data
tags:  device_id=gw01, area=A馆   (低基数、常过滤的字段)
fields: temp=25.3, hum=60          (会变化的数值)
```

**Tag 用于索引过滤，Field 存数值** —— 把高基数字段（设备 UUID）放进 tag 是性能分水岭。

TDengine 超级表对应：一个设备类型一张超级表，每个设备自动建子表，tag=设备属性。

## 4. 上云写入链路

```text
设备 → MQTT → EMQX → Webhook/规则 → 批量写 TSDB
                或 → Kafka 削峰 → 消费者批量写
```

要点：
- **批量写**：攒 100 条或 1 秒一批，单条写能把库打挂
- 时间戳用设备端时间（UTC 毫秒），别用服务器收到的时间
- 乱序数据：选支持乱序写入的库，或按水位线丢弃

## 5. 降采样与保留策略

```sql
-- InfluxDB 示意：原始数据留 7 天，1 分钟聚合留 1 年
CREATE RETENTION POLICY raw ON iot DURATION 7d REPLICATION 1
CREATE CONTINUOUS QUERY cq_1m ON iot BEGIN
  SELECT mean(temp) INTO iot."1m".device_data
  FROM iot.rp_raw.device_data GROUP BY time(1m), *
END
```

口诀：**明细保近期，聚合存长期，看趋势永远打聚合表。**

## 6. 查询模式速查

- 最新值：last() / 子查询按时间倒序 limit 1
- 区间聚合：`GROUP BY time(5m)` + mean/max/min
- 异常检测入门：滑动窗口 z-score（超过均值 3σ 告警）

## 7. 数据质量三查

1. **时间戳对不对**：NTP 漂移、时区混用
2. **单位统一没**：℃ 还是 ℉，kWh 还是 W
3. **心跳在不在**：设备掉线 vs 数值异常，先看最后上报时间
