# 边缘计算与网关架构速查

## 1. 为什么要边缘

| 痛点（纯上云） | 边缘解法 |
|---|---|
| 断网就瘫 | 边缘自治，网恢复再同步 |
| 实时性不够（ms 级控制） | 本地闭环 |
| 全量上云带宽贵 | 本地过滤/聚合，只传有用数据 |
| 视频上云泄密风险 | 本地推理，只传事件 |

## 2. 网关的三层职责

```text
南向：Modbus/Can/BLE/Zigbee... 千军万马接设备
北向：MQTT/HTTPS 单通道上云
本地：规则引擎 + 数据缓存 + 断点续传 + 本地 Web/UI
```

口诀：**下接百怪，上走一路，中间长脑子。**

## 3. 数据流设计模式

1. **直通**：传感器 → 网关 → 云（透明转发，最简单）
2. **过滤**：变化超阈值才发（死区 Deadband，能砍 80% 流量）
3. **聚合**：1 分钟窗口求均值/最大值，一条消息替代 60 条
4. **边缘决策**：温度 > 85℃ 本地直接关阀门，同时上报事件

## 4. 断网续传设计要点

- 本地环形缓冲（SQLite/文件），按时间戳排队
- 重连后按序补传，云端要有幂等/去重（时间戳或自增 id 判重）
- 补传限速，避免挤占实时流（QoS 隔离：实时 topic 高优，补传低优）

## 5. 软件选型速览

| 层 | 轻量方案 | 重型方案 |
|---|---|---|
| 运行时 | Node-RED / Python | K3s + 容器 |
| 本地 broker | Mosquitto | EMQX Edge |
| 规则 | 自写脚本 | eKuiper / Node-RED |
| 云协同 | AWS IoT Greengrass / Azure IoT Edge | 自建组件 |

## 6. 硬件画像

- 轻量网关：ESP32 做协议桥（BLE→MQTT），几克功耗
- 主流网关：树莓派 / 工控 RK3568 板，跑 Python + SQLite
- 重载边缘：x86 工控机，跑视频推理、容器编排

## 7. 可靠性清单

- [ ] 看门狗 + systemd 自动拉起
- [ ] 断电安全：SQLite WAL 模式，别裸写 JSON 文件
- [ ] OTA：网关自身也要能远程升级（分批灰度）
- [ ] 本地时间：NTP + RTC 电池，时间戳错乱是数据分析的天敌

> 网关的本质：**把「不可靠的现场」翻译成「可靠的云端语言」。**
