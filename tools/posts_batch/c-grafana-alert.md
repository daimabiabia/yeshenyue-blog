# Grafana 告警体系：从曲线好看 到 值班手机响

> 看板只能"看见问题"，告警才能"解决问题"。从曲线到值班手机的最后一公里，决定监控体系是不是摆设。

## 一、告警设计的三个反模式

1. **告警风暴**：一条规则刷 200 条通知 → 值班人开始无视告警（"狼来了"效应），真正的事故被淹没。
2. **无人认领**：告警发到群里没人 @ 责任人，48 小时无人处理。
3. **只测 symptoms**：CPU 高告警了，但用户已经故障 2 小时——告警应该贴着"用户可感知"设计。

健康告警体系 = **少而准 + 有人管 + 有处理手册**。

## 二、Grafana Alerting 配置要点

### 贴着用户可感知设计规则

```
❌ CPU > 80% 告警          ← 忙≠故障
✔ 数据断流告警：设备心跳 absent > 10min
✔ 数据质量告警：传感器 NaN 率 > 5% (5m)
✔ 业务阈值告警：冷库温度 > 8℃ 持续 10min
```

### 防风暴三件套

```yaml
# 1. pending period：持续超过阈值才触发（滤掉瞬时毛刺）
for: 5m

# 2. 通知合并：同一规则 30 分钟内只发一次，恢复才发第二条
repeat_interval: 4h
group_interval: 5m

# 3. 标签路由：按 severity 分流
labels:
  severity: critical | warn
```

### Alertmanager 路由示例

```yaml
route:
  receiver: default-warn
  group_by: [alertname, device]
  group_wait: 30s        # 聚合 30s 内同组告警为一条
  routes:
    - matchers: [severity="critical"]
      receiver: oncall-sms       # 严重：电话/短信
    - matchers: [severity="warn"]
      receiver: team-feishu      # 一般：群消息
```

## 三、IoT 场景必配的六条规则

1. **设备离线**：`absent(heartbeat[10m])` —— 最重要的一条。
2. **数据停止**：有连接但 `_measurement` 无新点 >30min（半死机）。
3. **数据质量**：NaN/超物理量程占比超限（传感器坏了）。
4. **通信质量**：MQTT 授权失败计数增长（有人试密码，安全告警）。
5. **电量**：电池设备 <20%（提前换电池，而不是等它死）。
6. **积压**：队列/缓冲区水位高（下游写入故障的早期信号）。

## 四、告警内容可执行

一条好告警自带上下文，值班人不需要打开 5 个页面拼线索：

```
标题：[critical] 冷库-03 温度超限
正文：
  当前 8.6℃，阈值 8℃，已持续 12min
  设备 esp32-freezer-03，最后心跳 2min 前（在线）
  最近 1h 趋势：持续上升无回落
  可能原因检查单：
  1) 门未关严（门磁最近 30min 有 3 次开启）
  2) 压缩机供电（该回路电流最近有波动）
  运维手册：https://wiki/.../freezer-incident
```

把**检查单写进告警**，是低成本高回报的运维投资。

## 五、值班与闭环

1. **认领机制**：告警必须被 ack（企业微信/飞书机器人支持按钮回复）。未 ack 15 分钟升级到下一级。
2. **处理结果回写**：故障单链接附在告警里，关闭告警必须关闭单子——防止"静默恢复"没人知道发生了什么。
3. **复盘**：每次 critical 事后 10 分钟"错题本"：为什么没提前发现？规则要不要加？

## 六、测试你的告警（重要且常被忽略）

```
每月一次"故障演习"：
1. 手动拔掉一台设备 → 计时看告警多久到、内容是否准确
2. 人为制造 NaN → 看数据质量告警是否触发
3. 关掉通知渠道 → 确认备用通道能兜底
```

没演习过的告警体系 = 没练过的消防栓。
