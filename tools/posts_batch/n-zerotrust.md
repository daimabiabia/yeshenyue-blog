# IoT 设备零信任入门：设备身份与最小权限

> "内网是可信的"这个假设已经过时——设备先被攻破的时代，每个设备都要有身份、有边界、有最小权限。

## 一、零信任在 IoT 里的三句话

1. **每次连接都验证**：设备与 broker/云之间不是"连上就算"，而是双向身份校验。
2. **只给刚好的权限**：温湿度传感器没有任何理由能发"开门"指令。
3. **假定已被攻破**：任何一台设备沦陷，横向影响面要被架构限制住。

## 二、设备身份的三种实现（按强度递增）

### 1. 用户名密码（现状基线）

```
每设备独立凭证（拒绝全网共用）
密码来自设备首次激活时生成，不入固件镜像
泄露影响面 = 单台设备
```

### 2. X.509 证书 + TLS 双向认证（推荐）

```
每设备：唯一私钥（烧录在安全区/NVS 加密）+ 设备证书
Broker/云：持有 CA 根证书，验设备证书链
设备：验证服务器证书（防假服务器）
结果：冒用设备 impossible，私钥不出设备
```

ESP32 落地：`esp_tls` 双向证书 + 出厂时写入唯一证书；吊销用 CRL/OCSP 或短有效期证书+在线续期。

### 3. 安全芯片（高价值设备）

ATECC608 / SE050 类：私钥生成于芯片内部、物理不可读，签名在芯片内完成。板子被拆也拿不走身份。成本 +3~5 元，按设备价值决定。

## 三、最小权限的落地：三层配额

```
网络层：设备只能访问 broker 的 8883 端口（防火墙/ACL）
应用层：topic 只能发 dev/<自身ID>/# （broker ACL）
功能层：指令白名单——传感器固件里根本没有"开门"代码可调用
```

**功能层最容易被忽略**：即使 broker 被攻破，攻击者向传感器发 `open_lock` 也无效——因为它没实现这个 handler。权限不只是"配置"，更是"能力边界"。

## 四、信任的建立：首次配对（Onboarding）

设备出厂是"白板"，怎么建立第一信任？

```
方案 A（私有云）：扫码绑定
  设备贴二维码（内含激活码）→ 用户 App 扫码 → 云端把激活码与账号绑定
  设备首连用激活码换证书/凭证 → 后续用证书

方案 B（自建家庭）：本地配对
  设备 AP 模式 → 手机连入 → 交换 WiFi 凭证 + 设备加入本地 ACL

共同纪律：激活凭证一次性、有时效；配对窗口 5 分钟自动关闭。
```

## 五、运行期的持续验证

1. **心跳 + 行为基线**：设备每分钟上报频率稳定在 ±20%，突变（风暴上报/静默）触发审查。
2. **固件完整性**：安全启动（secure boot）+ 签名固件，篡改的固件无法启动——ESP32 eFuse 开启即可。
3. **会话短命**：TLS 会话 24h 强制重协商；token 有效期短 + 续签。
4. **异常指令熔断**：设备收到不认识的 topic/指令次数超限 → 主动断连 + 上报 + 进入"只上报不执行"模式。

## 六、攻破假设演练（架构自检）

问自己五个问题：

```
1. 拿到一台设备固件，能提取出"万能密钥"进全网吗？
   （能 = 用了全局共享密钥，重做）
2. 一台设备被完全控制，能操控别的设备吗？
   （能 = ACL 没做水平隔离）
3. Broker 数据库泄露，能伪造任意设备上线吗？
   （能 = 私钥在云端集中保管）
4. 用户密码泄露，能直接下发危险指令吗？
   （能 = 高危指令缺二次确认/双向认证）
5. 设备离线时的指令队列，会被重放吗？
   （会 = 指令缺时间戳/nonce 防重放）
```

## 七、起步清单（小项目也能做）

- [ ] 每设备独立凭证，激活时生成
- [ ] TLS 双向认证（自建 CA 起步即可）
- [ ] broker ACL 按 topic 前缀隔离
- [ ] 高危指令带 nonce+时间戳防重放
- [ ] 固件签名 + secure boot
- [ ] 设备行为有基线监控
